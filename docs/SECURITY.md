# Security

## Threat model in one paragraph

This kit runs on your machine with your privileges, launches coding agents
**with permission prompts disabled**, and holds provider API keys. The risks
that matter are therefore: a key leaking into git, a log, a shell history or a
shared config file; a wrapper launching the wrong binary; an installer piping an
unexpected script into a shell; and a config writer destroying something you
wrote yourself.

## Where secrets live

- **Only** in your env file: `~/.config/coding-agents-kit/env` (`chmod 600`) or
  `%APPDATA%\coding-agents-kit\env` (ACL restricted to you). Created from
  `env.example`, which contains **names only**, and never overwritten afterwards.
- Wrappers `source` it with `set -a` (or parse it, on Windows) so values are
  exported to the wrapper's own process and the CLI it launches — nothing else.
- Not in this repository, not in your shell rc, not in any generated config.
- `grok login` (OAuth) is the preferred Grok auth; `XAI_API_KEY` is optional for
  `grokx` and required only for the `*-xai` wrappers.

## What the kit writes, and how secrets are referenced

| File | Reference form | Notes |
| --- | --- | --- |
| `<CODEX_HOME>/<provider>.config.toml` | `env_key = "ZAI_CODING_API_KEY"` | kit-owned overlay; rewritten on every launch |
| `opencode.json` | `"apiKey": "{env:XAI_API_KEY}"` | user-owned; only `provider.<id>` merged; global `model` untouched; refuses invalid JSON; one-time `.agentkit.bak` |
| `~/.pi/agent/models.json` | `"apiKey": "$AZURE_OPENAI_API_KEY"` | user-owned; only `providers.<id>` upserted; same rules |
| `claude-glm` | nothing on disk | `ANTHROPIC_*` variables set for the process only |
| `~/.ssh/config.d/coding-agents-kit` | no secrets at all | generated by `agentbox ssh-config --write`: host names, ports, user names; atomic write, `chmod 600`, provenance header |
| `~/.ssh/config` | **never written** | the one `Include` line is printed for you to add |
| your env file | **never overwritten** | created once, from names only |

## Known exception: Cline receives the key on argv

`cline auth -p openai -b <url> -k <key> -m <model>` and `cline --yolo … -k <key>`
put the value on the command line. It can appear in the process list and in
shell history. Mitigations:

- zsh: `setopt HIST_IGNORE_SPACE` and type the command with a leading space.
- bash: `HISTCONTROL=ignorespace`, same trick.
- PowerShell: `Set-PSReadLineOption -HistorySaveStyle SaveNothing` for that
  session, or remove the line from `(Get-PSReadLineOption).HistorySavePath`.
- Or simply do not use `cline-azure` / `cline-xai`; `clinex` with Cline's own
  auth does not take a key on argv.

No env-reference mechanism for Cline was found when this was written. If one
exists now, this exception should disappear — that is a welcome pull request.

## The `herdr` subprocess

Machine ids, labels and targets are parsed out of `herdr machine list --json`
and passed back as **separate arguments**, never through a shell. A hostile
label or target cannot break out into command execution; `tests/run.sh herdr`
asserts it with a stub whose label and id contain `;`, `$( )` and backticks, on
both the bash and the Python side. Every failure path — herdr absent, machine
absent, call failed — warns once and **never** changes the caller's exit code.

## Host only

`agentkit onboard` and the mutating `agentbox` verbs refuse to run inside a
container and say how to reach a host shell. They write to your home directory,
drive Docker and move Herdr machines; doing that against a container's own
filesystem would be silently wrong rather than useful. Read-only verbs still run
and say whose PATH they are reporting.

## Installer posture

- Official vendor URLs only. If one 404s, the kit prints the vendor's docs link
  and continues — it never points at a mirror and never guesses a package name.
- Node packages by exact name: `@openai/codex`, `cline`,
  `@earendil-works/pi-coding-agent`.
- Nothing is uninstalled, moved or re-linked. Cursor's installer replaces the
  `agent` entry point on some systems; the kit warns before that happens on a
  machine that has Grok.
- `curl | bash` is the documented path for several of these vendors. If you do
  not accept that, install those CLIs by hand and run `agentkit status` — the
  kit will detect and keep them.

## Full-permission flags

`--dangerously-skip-permissions`, `--dangerously-bypass-approvals-and-sandbox`,
`--force`, `--auto`, `--approve`, `--yolo` are the point of the wrappers. They
belong in your own terminal, on a machine you control, on code you are willing
to let an agent change. Do not run them in CI, on a shared host, or for an agent
whose prompt you do not control.

## What must never be committed to this repository

- Any real key, token or session id — even a fragment, even redacted-looking.
- Anyone's `~/.ssh/config`, `known_hosts`, `auth.json` or Herdr `endpoints.json`.
- A real host name, internal port map, employer name or private repository URL.

`tests/run.sh lint` greps the tree for key-shaped strings and for
company-specific references. Keep both checks.

## Reporting a problem

Open an issue at
<https://github.com/xergioalex/coding-agents-setup-kit/issues>. If the finding
involves a secret you found leaking, describe the class of problem — never paste
the value.
